Adopter-facing summary, updated 2026-11-09. The working backlog, ranked and
with a status line on every item, is [`docs/ROADMAP.md`](./docs/ROADMAP.md)
("Current priorities"). Where things stand, kept apart as shipped, merged but

[`docs/DELIVERY_PLAN.md`](./docs/DELIVERY_PLAN.md). This file's earlier text

## What you can use today

- **Libraries** `dev.keliver:*:0.4.1` on Maven Central: the runtime (a fork of
  Cash App Redwood on Zipline), the `keliver-material` widget set, layout and
  lazy layouts, navigation, HTTP and SQL capabilities, and the portal's editor
  libraries. Pre-1.0: pin an exact version ([`docs/API_STABILITY.md`](./docs/API_STABILITY.md)).
- **Tools bundle** `keliver-portal-tools` 0.3.18 (a GitHub release asset):
  `keliver-init` scaffolds an app, `keliver-portal` runs the relay and the
  visual editor, `keliver-run-android` puts the app's screens on a phone or
  emulator (checked on the CI emulator and a physical Android phone),
  `keliver-publish` writes signed bundles for any static HTTPS server, and
  scaffolders write a production host for Android and iOS (also embeddable in
  an existing app) and a per-app editor.
- **Production delivery**: Ed25519-signed, versioned bundles, a rollback floor,
  channels and staged rollout, signing-key rotation, updates on resume, and
  reports, all verified by the host before any code runs.

Start here: [`docs/GETTING_STARTED.md`](./docs/GETTING_STARTED.md), then
[`docs/PORTAL_ADOPTER_GUIDE.md`](./docs/PORTAL_ADOPTER_GUIDE.md).

## Next

From 2026-11-09 the plan is [`docs/PLAN_2026-11.md`](./docs/PLAN_2026-11.md). In order:

1. **Writing a screen is writing Compose.** The guest API is to be generated from
   Compose's own API: the same names, parameters, types and slots, with only the
   imports different. Hosts draw with the real Compose functions, so screens look
   and move exactly like native ones. It ships in libraries **0.5.0**, with Kotlin
   2.4.20 and the generated bridge code.
2. **The editor for teams:** every state of every screen with real or recorded
   data, safe edits, a preview on a phone from a link, change requests with
   screenshots, publishing with a rollout percentage, and rollback.
3. **Tools for coding agents:** `keliver check` with machine-readable results,
   rendered states an agent can see, an `llms.txt`, and agent guides in new apps.
4. **Delivery operations:** crash rollback on the device, a release view, a CI
   action, and smaller updates.
5. **A physical-device proof** with release-signed builds and a real HTTPS
   server, and an external adopter.

Done since 2026-10, in tools 0.3.13 to 0.3.18: live updates on both hosts, the
host kit for existing apps, the dependency-floor report, HostHttp through the
app's own client on both platforms, start-up and memory profiles, and the bridge
gate with hosts that serve an app's bridges. The list this replaced is in git
history.

## Deliberately out of scope

- **View, UIView and DOM widget systems.** Keliver is Compose Multiplatform
  only; for Android Views, UIKit or the browser DOM, use upstream
  [Cash App Redwood](https://github.com/cashapp/redwood).
- **The Zipline runtime itself.** Keliver builds on
  [`app.cash.zipline`](https://github.com/cashapp/zipline); QuickJS and Zipline
  compiler-plugin bugs (e.g. `docs/KNOWN_BUGS.md` U8 part 1) are filed there.
- **AI-generated UI at runtime.** The schema is a static contract between guest
  and host; UI generated by a model that has never seen it is a different
  problem.

## How to influence the roadmap

Open an issue with the problem you hit and what you were building. Evidence
from a real app moves an item up: every item in `docs/ROADMAP.md` names the
evidence behind it.
