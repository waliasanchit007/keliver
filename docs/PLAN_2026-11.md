**Status: plan of record from 2026-11-09**, agreed with the owner. It sets the direction and
the order of work. [`DELIVERY_PLAN.md`](DELIVERY_PLAN.md) keeps the step-by-step record and its

## 1. What Keliver is for

**The pitch: Compose that ships without a store release.**

- **For:** new screens, and features an app keeps on the web today so that it can change them
  without a release (WebView screens become native screens).
- **Not for:** porting an app's existing native screens. A static scan (2026-11-08) of a
  production Android app's Compose code found that almost every screen file uses something a
  guest cannot run: ViewModels with dependency injection, Android APIs, resources or native SDKs.
  A port is a rewrite.
- **Who uses it:**
  - developers, who on the owner's working assumption now work mostly through coding agents;
  - product managers and designers, through the web editor: they see every real state of a
    screen and change what they need, safely, without waiting for a developer;
  - release owners, through signed delivery: channels, staged rollout, rollback and reports.

## 2. The bar

1. **Writing a guest is writing Compose.** The same names, parameters, types, defaults and
   slots as Compose; only the imports differ (`dev.keliver.compose.*`). A developer or a coding
   agent learns nothing new.
2. **What Compose Multiplatform can draw, lay out or animate declaratively, a guest can use.**
   The exceptions are per-frame escape hatches (custom `Layout {}` measuring, raw pointer
   handlers) and platform APIs, which fail at compile time (point 5). A new design waits for an
   app release only when it needs a genuinely new native capability.
3. **Identical to native, at rest and in motion**, because the host draws with the real Compose
   functions.
4. **Business logic lives in the guest, in a sandbox:** data through `HostHttp` on the app's own
   client behind a `RequestPolicy`, actions through generated bridges.
5. **What cannot work fails at compile time**, and the error names the alternative.
6. **The editor shows real states and round-trips safely:** every state of a screen, with real
   or recorded data; edits write back as minimal Kotlin diffs (D4, D14), with 0 `RawCode` for
   screens within the editor's supported subset.
7. **Agent-first tooling:** every check an agent needs runs from the command line with
   machine-readable output, and an agent can see what it built (rendered states).
8. **Safe delivery** (built): signed, versioned and gated bundles, a rollback floor, channels,
   staged rollout, reports and key rotation.
9. **Measured, not claimed:** API parity by a same-source test corpus, fidelity by golden screens,
   speed and memory on a real mid-range phone.

## 5. Workstreams

### WS1. Foundation
Kotlin 2.4.20 with Zipline 1.28.0 (which is built on 2.4.20), and the Compose Multiplatform and
AndroidX Compose versions that match. The whole build and CI green, `apiCheck`, U14's tripwire
(re-run the two ignored `ProtocolTest`s at a Kotlin or Compose bump), and D4's byte-stable
write-back re-proven, because the ingest and codegen use `kotlin-compiler-embeddable`. No library
is published until 0.5.0. A tools release in between, if any, is cut from a commit before MS1's
merge, or its bundled development host and generic editor are first checked against guests built
with Zipline 1.22.0; its scaffolders keep today's pins (Kotlin 2.2.0, Zipline 1.22.0).

### WS2. The Compose-generated API (if Gate B confirms PD2)
- **A generator** reads Compose's published API and sources (Material 3, foundation, the UI
  modifiers, animation) and emits:
  - guest functions with Compose's exact signatures, in `dev.keliver.compose.*`;
  - the wire schema, with stable tags that are only ever appended (a lock file);
  - host renderers that call the real Compose function, with defaults taken from Compose's source;
  - editor metadata: palette group, property kinds, documentation.
- **Written by hand, once:**
  - value codecs: `Dp`, `TextUnit`, `Color`, `Brush`, `Shape`, `TextStyle`, `FontWeight`,
    alignments, arrangements, `PaddingValues`, icons, the `*Defaults` factories, modifier chains;
  - theme references: `MaterialTheme.colorScheme.primary` and the type scale resolve on the host;
  - state objects owned by the host and mirrored to the guest by events: `LazyListState`,
    `PagerState`, `SheetState`, `ScrollState`.
- **Per-frame APIs:**
  - declarative animation (`AnimatedVisibility`, `AnimatedContent`, `Crossfade`,
    `animateContentSize`, enter and exit specs, `animateItem`) is generated and runs on the host;
  - `animate*AsState` runs in the guest or on the host, decided by Gate B's measurement;
  - `Canvas` works by recording drawing commands in the guest and replaying them on the host;
  - custom `Layout {}`, raw pointer handlers and Android APIs are compile-error stubs that name
    the alternative.
- **An app's own components** are exported to guests by explicit opt-in only (some start payments
  or native flows). They must be multiplatform to appear in the editor.
- **The compatibility gate (extends D2):** the widget groups, generated-API version and app
  components a bundle needs become signed manifest metadata and index `constraints`; hosts skip
  such a bundle at lookup and refuse it at load, as item 4's B4 does for bridges.
- **Legacy and size:** today's hand-written widgets stay as a legacy schema, and a migration tool
  converts screens written against today's API. Widget groups keep app size in check.

### WS3. Logic and bridges
Item 4's B5c (the contract build: its modules ship in 0.5.0, its template properties and scaffolder
flags in the tools release after it); B5b on the iOS simulator (a test); `keliver.bridges` written
from the generated constants; B5d's §5 (the reference app on a real generated bridge) after 0.5.0.

### WS4. The editor (flagship)
In a team where agents write most of the code, the editor is where people see every state of
every screen, make safe changes, and approve what ships.
- **ED0. The generated catalog.** The canvas calls the real Compose functions on wasm, so the
  canvas draws what a device draws. The grammar reads Compose-shaped code (slots, `16.dp`, theme
  references, modifier chains), with 0 `RawCode` for screens in the supported subset and
  byte-stable write-back. Needs D6 and D9 amended (section 4); until then it stays on a branch.
- **ED1. Named states.** `@ScreenState` next to a screen (a typed route and a fixture set); data
  recorded by the relay's secure capture and usable on devices; the editor lists and previews
  every state (item 5's S1–S2).
- **ED2. Live without mappers.** Generated live adapters for each Bindings interface, so Live
  runs an app's real presenters with no hand-written mapping (adoption finding 9; it needs
  `keliver-nav` on wasmJs).
- **ED3. On a phone.** A link or QR code opens the edited state on a debug emulator or phone,
  through a built-in device proxy that serves `GET /bundles/*` only (item 6's open row).
- **ED4. Change requests.** An edit becomes a branch and a pull request with before-and-after
  screenshots of every affected state. An approver merges; the editor publishes to a channel
  with a rollout percentage; a release view shows adoption, failures and a rollback button.
- **ED5. Hosted for a team.** The relay as a team service with sign-in, roles, an audit log and a
  build queue. Designed and reviewed for security first (U35 and U36 are why it is local today).
  Until then a product manager uses the editor on a developer's machine, or reviews through CAP6's
  links.
- **ED6. Ask for a change.** A product manager describes a change; an agent makes it through MCP;
  it arrives as a change request with screenshots.

### WS5. Agent-first tooling
- `llms.txt` and an agent guide generated from the catalog; scaffolded apps get the agent files
  D15 asks for (`CLAUDE.md`, `ARCHITECTURE.md`, `WORKFLOW.md`).
- `keliver check`: compile, editor compatibility, unsupported APIs, the bundle budget, and state
  screenshots against goldens, with machine-readable output.
- MCP tools to render a state to PNG, run it on the emulator or simulator, and publish to a
  preview channel.
- Run scripts for both platforms (`keliver-run-android` exists; an iOS simulator one is added).
- A Claude Code plugin with skills: new screen, add a state, preview, publish.

### WS6. Delivery operations
- **Crash rollback on the device:** a bundle that fails N times on one install is set aside, the
  host returns to the previous good one, and the report says so.
- The release view (shared with ED4).
- A CI action that sets up, publishes and uploads.
- Deterministic, smaller updates (item 7: a one-line change re-sends the standard-library module).
- A release-size report: what Keliver adds to the app.
- The snapshot runner on the emulator and simulator (item 5's S3–S4), on an emulator image whose
  screenshots are valid (section 7).

### WS7. Performance
Item 2's M4 composition/encoding split ships in 0.5.0 (MS4). Tree size and first frame under the
generated API are measured at Gates A and B. The optimisation decision from item 2's M2–M5 is
taken at MS8, with phone checkpoints on the A12 and the iPhone.

### WS8. Proof and adoption
- A private three-way comparison on the 2026-10 product proof's feature: the web page, today's
  API and the generated API. Its code and measured values stay out of this repository; each
  gate's verdict, criterion by criterion, goes in, and a generic retro follows, as
  `ADOPTION_RETRO_2026-10.md` did.
- The reference app ported to the generated API: public evidence in CI.
- W7: release-signed APK and IPA, HTTPS with a real certificate, item 3's K4 on an iPhone.
- One to three design partners; docs compaction; the README and the pitch.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Compose-faithful trees have more nodes, so the first frame is slower | Measured at Gate A; batching and a binary encoding later if needed |
| App size: renderers for all of Material 3 stop R8 from removing unused components | Widget groups; measured at Gate B |
| Compose's API keeps changing | Generate per Compose version; pin a supported subset; append-only tags |
| The editor's grammar against the whole of Compose | The editor covers the common subset; everything else still compiles and runs, as `RawCode` |
| Per-frame code in the guest is slow | Declarative APIs run on the host; measured; a lint check |
| Kotlin compiler internals: the ingest and codegen use `kotlin-compiler-embeddable` | MS1's gate re-proves byte-stable write-back on 2.4.20 |
| The dependency floor (item 3's K3) rises for apps that embed a host | The floor report shows it before anything is written; called out in the 0.5.0 notes |
| Store policy (interpreted JavaScript) | The sandbox; no native code in bundles; guidance against using updates to bypass review for major changes |
| Security of a hosted editor | Design and review before building; sign-in, roles, an audit log; the relay's write routes never exposed without authentication |
| One maintainer | The generator lowers upkeep; coding agents; this documented process |

## 12. Out of scope, or parked

## 13. How work is done

Unchanged:
- Each item is a pull request with an independent read-only review, merged only when every
  check on its exact head has passed.
- Records are kept current.
- Tools releases go out when their checks pass; libraries releases need the owner's go.

New in this round:
- The emulator and simulator by default, the phones at checkpoints.
- Code and measured values from a private app never enter this repository; each private gate's
  verdict, criterion by criterion, does.

## 14. Moving fast

Added 2026-11-10, after the owner said development had become too slow. Measured then: an
`ios-host` run took 166–175 minutes on a pull request (one took 366), `reference-app` 39–47 and
`ci.yml` 21–26; one full review of a docs pull request took 4.4 hours; about a third of recent pull
requests only updated records; each fix push restarted hours of CI; superseded runs were
cancelled by hand. The rules from now on:

- **Reviews are tiered and time-boxed.** Docs and records: a check of the diff's own claims, about
  15 minutes. Code: an independent review of the diff and its tests, about 45–60 minutes,
  blockers and mediums first. Low findings are listed and ship with the next pull request, never
  as an extra push that restarts CI. A re-review reads the delta only. The review starts when the
  pull request opens, in parallel with CI.
- **No record-only pull requests.** Records travel with the change they record. Between milestone
  gates and releases only `DELIVERY_PLAN.md`'s row changes; `CURRENT_STATE.md`, both roadmaps and
  the adoption plan change at gates and releases.
- **Check before pushing:** `scripts/prepush.sh` runs, for what the branch changed, the docs check,
  `actionlint` and `shellcheck` (when installed), each changed module's test tasks and `apiCheck`,
  and the generated-code freshness check; it prints which CI device jobs the change will trigger.
- **One reviewable pull request per milestone step**, the two tracks in parallel.
- **CI:**
  - A newer push to a pull request cancels the older run of `ci.yml`, `reference-app.yml` and
    `ios-host.yml`. Runs of the device workflows on main (pushes, the nightly run, runs started by
    hand) never cancel each other.
  - A pull request that changes only Markdown skips `ci.yml`'s build and the embed floor, unless
    it changes Markdown the build reads (`docs/PORTAL_ADOPTER_GUIDE.md`, bundled into
    `portal-mcp` and tested). Its check is the docs job (`scripts/docs-check.sh`: relative links,
    table shapes, and a hygiene grep on the lines it adds outside test sources; names that must
    never appear stay in an untracked local list).
  - `ios-host` runs the scaffolder self-test and the OTA route as two jobs at once. On a pull
    request that touches none of what T2 checks (the host's Kotlin, its app shell, its build
    configuration, the timing harness), it skips T2's two release-type builds (about 50 minutes);
    main, a nightly run and a run started by hand run everything. The repository variable
    `IOS_RUNNER` can route it to a faster runner.
  - Caches: hosted runners restore the Kotlin/Native toolchain and Gradle's downloads (`ios-host`)
    and Gradle's downloads (`reference-app`, which now also runs on pushes to main). The jobs set
    `GRADLE_USER_HOME` and `KONAN_DATA_DIR` explicitly, because the harness moves `user.home` into
    its work directory. Only runs on main save a cache, so pull requests do not crowd the
    repository's cache space; a run started by hand, the published-only proof, never restores one.
  - Targets: `ios-host` under 45 minutes and `reference-app` under 25 on a pull request. On hosted
    runners the changes above are not expected to reach them (the self-test job and skipping T2
    save about 70 of `ios-host`'s minutes; the rest is about eight Kotlin/Native and `xcodebuild`
    builds). `DELIVERY_PLAN.md`'s row records the first measured runs. The rest needs a faster
    runner (the owner's call) or the static route split into its own job, a follow-up in MS0.
- **Wait in the background:** on CI and on agents, never in the foreground.
- **Short** pull request bodies and commit messages.
