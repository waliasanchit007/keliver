# Keliver plan, 2026-11: Compose that ships without a store release

**Status: plan of record from 2026-11-09**, agreed with the owner. It sets the direction and
the order of work. [`DELIVERY_PLAN.md`](DELIVERY_PLAN.md) keeps the step-by-step record and its
evidence, [`ROADMAP.md`](ROADMAP.md) ranks the backlog, and [`CURRENT_STATE.md`](CURRENT_STATE.md)
says what is true today. Where an older plan disagrees with this one, this one wins. It is
revisited at every gate in section 8.

## 1. What Keliver is for

**The pitch: Compose that ships without a store release.**

- **For:** new screens, and features an app keeps on the web today so that it can change them
  without a release (WebView screens become native screens).
- **Not for:** porting an app's existing native screens. A static scan (2026-11-08) of a
  production Android app's Compose code found 81 screen files, and only one of them used nothing
  a guest cannot run. The others use ViewModels with dependency injection, Android APIs,
  resources or native SDKs, so a port is a rewrite.
- **Who uses it:**
  - developers, who now work mostly through coding agents;
  - product managers and designers, through the web editor: they see every real state of a
    screen and change what they need, safely, without waiting for a developer;
  - release owners, through signed delivery: channels, staged rollout, rollback and reports.

## 2. The bar

1. **Writing a guest is writing Compose.** The same names, parameters, types, defaults and
   slots as Compose; only the imports differ (`dev.keliver.compose.*`). A developer or a coding
   agent learns nothing new.
2. **Anything Compose Multiplatform can draw, lay out or animate, a guest can use.** A new
   design waits for an app release only when it needs a genuinely new native capability.
3. **Identical to native, at rest and in motion**, because the host draws with the real Compose
   functions.
4. **Business logic lives in the guest, in a sandbox:** data through `HostHttp` on the app's own
   client behind a `RequestPolicy`, actions through generated bridges.
5. **What cannot work fails at compile time**, and the error names the alternative.
6. **The editor shows real states and round-trips safely:** every state of a screen, with real
   or recorded data; edits write back as minimal Kotlin diffs (D4, D14).
7. **Agent-first tooling:** every check an agent needs runs from the command line with
   machine-readable output, and an agent can see what it built (rendered states).
8. **Safe delivery** (built): signed, versioned and gated bundles, a rollback floor, channels,
   staged rollout, reports and key rotation.
9. **Measured, not claimed:** API parity by a same-source test corpus, fidelity by golden screens,
   speed and memory on a real mid-range phone.

## 4. Decisions in this round

| | Decision | Why |
|---|---|---|
| P1 | The pitch is new screens and web screens made native, not ports | The scan in section 1 |
| P2 | **Generate the guest API from Compose's own API and sources; the host calls the real Compose function** | Identical to Compose by construction; coverage by default; one generator instead of copying by hand forever. Confirmed or dropped at Gate B (M3) |
| P3 | A Shorebird-style on-device interpreter (patching changed Kotlin functions) is **parked** | A different product (hotfixes of existing Android Kotlin), and its risks are not engineering ones: Google Play's rule against self-updates, patched code running with the app's full privileges (no sandbox), release-build stripping against hooks and call tables, generated code (dependency injection) that cannot be patched, and interpreted code on the main thread. Revisited only for a customer who needs it and accepts the policy risk |
| P4 | One libraries release, **0.5.0**: Kotlin 2.4.20 and Zipline 1.28.0, the generated API, and the bridge modules | One approval, one migration for adopters |
| P5 | **The editor is the review and control surface**: see every state, make safe edits, preview on a device, approve, publish, roll back | Development is now mostly done by coding agents; people need to see and steer what ships |
| P6 | **Agent-first tooling is a workstream**, not documentation | The same reason |
| P7 | **Emulator and simulator by default; phones at planned checkpoints** | Comparisons on one machine are valid there; absolute speed and memory need a phone |

## 5. Workstreams

### T1. Foundation
Kotlin 2.4.20 with Zipline 1.28.0 (which is built on 2.4.20), and the Compose Multiplatform and
AndroidX Compose versions that match. The whole build and CI green; nothing published until 0.5.0.

### T2. The Compose-generated API
- **A generator** reads Compose's published API and sources (Material 3, foundation, the UI
  modifiers, animation) and emits:
  - guest functions with Compose's exact signatures, in `dev.keliver.compose.*`;
  - the wire schema, with stable tags that are only ever appended (a lock file);
  - host renderers that call the real Compose function, with defaults taken from Compose's source;
  - editor metadata: palette group, property kinds, documentation.
- **Written by hand, once:**
  - value codecs: `Dp`, `TextUnit`, `Color`, `Brush`, `Shape`, `TextStyle`, `FontWeight`,
    alignments, arrangements, `PaddingValues`, icons, the `*Defaults` factories, modifier chains;
  - theme references: `MaterialTheme.colorScheme.primary` and the type scale resolve on the host;
  - state objects owned by the host and mirrored to the guest by events: `LazyListState`,
    `PagerState`, `SheetState`, `ScrollState`.
- **Per-frame APIs:**
  - declarative animation (`AnimatedVisibility`, `AnimatedContent`, `Crossfade`,
    `animateContentSize`, enter and exit specs, `animateItem`) is generated and runs on the host;
  - `animate*AsState` runs in the guest or on the host, decided by Gate B's measurement;
  - `Canvas` works by recording drawing commands in the guest and replaying them on the host;
  - custom `Layout {}`, raw pointer handlers and Android APIs are compile-error stubs that name
    the alternative.
- **An app's own components** are exported to guests by explicit opt-in only (some start payments
  or native flows). They must be multiplatform to appear in the editor.
- **Compatibility:** today's 76 widgets stay as a legacy schema; a migration tool converts screens
  written against today's API. Widget groups keep app size in check.

### T3. Logic and bridges
B5c (the contract build and the scaffolder flags), B5b on the iOS simulator, `keliver.bridges`
written from the generated constants, all published in 0.5.0. Recorded HTTP data usable on
devices (adoption plan item 5, S2).

### T4. The editor (flagship)
In a team where agents write most of the code, the editor is where people see every state of
every screen, make safe changes, and approve what ships.
- **E0. The generated catalog.** The canvas calls the real Compose functions on wasm, so the
  canvas draws what a device draws. The grammar learns Compose-shaped code (slots, `16.dp`,
  theme references, modifier chains), still with 0 `RawCode` and byte-stable write-back.
- **E1. Named states.** `@ScreenState` next to a screen (a typed route and a fixture set); data
  recorded by the relay's secure capture; the editor lists and previews every state (adoption
  plan item 5, S1–S2).
- **E2. Live without mappers.** Generated live adapters for each Bindings interface, so Live
  runs an app's real presenters with no hand-written mapping (adoption plan item 9).
- **E3. On a phone.** A link or QR code opens the edited state on a debug emulator or phone,
  through a built-in device proxy that serves `GET /bundles/*` only (adoption plan item 6).
- **E4. Change requests.** An edit becomes a branch and a pull request with before-and-after
  screenshots of every affected state. An approver merges; the editor publishes to a channel
  with a rollout percentage; a release view shows adoption, failures and a rollback button.
- **E5. Hosted for a team.** The relay as a team service with sign-in, roles, an audit log and a
  build queue. Designed and reviewed for security first (U35 and U36 are why it is local today).
- **E6. Ask for a change.** A product manager describes a change; an agent makes it through MCP;
  it arrives as a change request with screenshots.

### T5. Agent-first tooling
- `llms.txt` and an agent guide generated from the catalog; scaffolded apps get an `AGENTS.md` /
  `CLAUDE.md` (D15).
- `keliver check`: compile, editor compatibility (0 `RawCode`), unsupported APIs, the bundle
  budget, and state screenshots against goldens, with machine-readable output.
- MCP tools to render a state to PNG, run it on the emulator or simulator, and publish to a
  preview channel.
- Run scripts for both platforms (`keliver-run-android` exists; an iOS simulator one is added).
- A Claude Code plugin with skills: new screen, add a state, preview, publish.

### T6. Delivery operations
- **Crash rollback on the device:** a bundle that fails N times on one install is set aside, the
  host returns to the previous good one, and the report says so.
- The release view (shared with E4).
- A CI action that sets up, publishes and uploads.
- Deterministic, smaller updates (adoption plan item 7: a one-line change re-sends the
  standard-library module).
- A release-size report: what Keliver adds to the app.
- The snapshot runner on the emulator and simulator (adoption plan item 5, S3–S4).

### T7. Performance
M4's composition/encoding split (in 0.5.0); the optimisation decision from M2–M5; tree size and
first frame under the generated API; checkpoints on the A12 and the iPhone.

### T8. Proof and adoption
- A private three-way comparison on the 2026-10 product proof's feature: the web page, today's
  API and the generated API. Its code and numbers stay out of this repository; a generic retro
  goes in, as `ADOPTION_RETRO_2026-10.md` did.
- The reference app ported to the generated API: public evidence in CI.
- W7: release-signed APK and IPA, HTTPS with a real certificate, K4 on an iPhone.
- One to three design partners; docs compaction; the README and the pitch.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Compose-faithful trees have more nodes, so the first frame is slower | Measured at Gate A; batching and a binary encoding later if needed |
| App size: renderers for all of Material 3 stop R8 from removing unused components | Widget groups; measured at Gate B |
| Compose's API keeps changing | Generate per Compose version; pin a supported subset; append-only tags |
| The editor's grammar against the whole of Compose | The editor covers the common subset; everything else still compiles and runs, as `RawCode` |
| Per-frame code in the guest is slow | Declarative APIs run on the host; measured; a lint check |
| Store policy (interpreted JavaScript) | The sandbox; no native code in bundles; guidance against using updates to bypass review for major changes |
| Security of a hosted editor | Design and review before building; sign-in, roles, an audit log; the relay's write routes never exposed without authentication |
| One maintainer | The generator lowers upkeep; coding agents; this documented process |

## 12. Out of scope, or parked

- The Shorebird-style interpreter (P3).
- UI generated by a model at runtime (A2UI-style): watched, not built; an official Compose
  renderer is planned by Google.
- SwiftUI rendering on iOS: only for an iOS-first adopter.
- Porting existing native screens (P1).

## 13. How work is done

Unchanged:
- Each item is a pull request with an independent read-only review, merged only when every
  check on its exact head has passed.
- Records are kept current.
- Tools releases go out when their checks pass; libraries releases need the owner's go.

New in this round:
- The emulator and simulator by default, the phones at checkpoints.
- Code and numbers from a private app never enter this repository; only generic retros do.
